# PaperOpenClaw 需求规格说明书

版本：v1.0
状态：已确认
适用产品：PaperOpenClaw —— 基于 OpenClaw 式智能体架构的论文知识库软件

---

## 1. 产品定位

PaperOpenClaw 是一套本地优先、跨操作系统的论文知识库软件。它把下载到的论文 PDF
批量解析入库，构建**金字塔式 RAG 语义库**与**鱼骨式知识图谱**，并在此之上提供
检索、基于库的问答、多智能体隔离头脑风暴，以及可扩展的 Skill 装载能力。

软件本身采用 OpenClaw 式智能体架构组织：网关（Gateway）负责通信，智能体运行时
（Agent Runtime）负责推理循环，工具注册表（Tool Registry）负责能力暴露，技能
加载器（Skill Loader）负责能力扩展，子智能体（Sub-agent）负责并行与隔离。

大模型一律通过 **API Key** 接入，不内置本地推理模型；软件不依赖任何必须常驻的
外部服务（数据库、消息队列、图数据库均为可选的本地嵌入式实现）。

### 1.1 设计原则

| 原则 | 说明 |
| --- | --- |
| 本地优先 | 所有论文、图表、向量、图谱落在本地数据目录，可整目录迁移与备份 |
| 零外部依赖 | 默认仅需 Python 与 Node 运行时，持久化用 SQLite + ChromaDB 嵌入式模式 |
| 跨操作系统 | Windows / macOS / Linux 同一套代码，路径一律用 `pathlib` 处理，不写死分隔符 |
| 内容寻址 | 论文以 SHA-256 哈希作为唯一身份与目录名，天然去重、可校验 |
| 接口先行 | 前后端以显式 API 契约对齐，前端不做后端未提供的假设 |
| 无图标界面 | 界面只使用文字按钮，不使用 emoji 或图形符号 |

## 2. 术语表

| 术语 | 含义 |
| --- | --- |
| 哈希 / Hash | 论文 PDF 字节流的 SHA-256 十六进制小写串，论文的唯一标识 |
| OKF | Open Knowledge Format（Google 开源，v0.2）：Markdown + YAML frontmatter 的知识包格式 |
| OKF Bundle | 一篇论文对应的一棵 OKF 目录树 |
| RAG 库 A | 金字塔最底层：由原文精简得到的详细大意，按章节切分 |
| RAG 库 B | 金字塔中层：由 A 再精简，按七个鱼骨维度归并 |
| RAG 库 C | 金字塔顶层：论文 abstract 原文 |
| 鱼骨 | 知识图谱的骨架维度：背景、数据、方法、实验、结论、讨论、不足与展望 |
| Skill | 以 `SKILL.md` 描述的能力包，可装载、启用、禁用 |
| 子智能体 | 拥有独立上下文、独立工具白名单、独立工作目录的智能体实例 |

## 3. 功能需求

### FR-1 PDF 入库与哈希编码

- FR-1.1 支持一次选择单个或多个 PDF 文件导入，也支持指定目录批量导入。
- FR-1.2 对每个 PDF 以流式方式计算 SHA-256，作为论文唯一标识。
- FR-1.3 入库前按哈希查重：已存在的论文默认跳过，并返回既有记录。
- FR-1.4 原始 PDF 保存在 `papers/<hash>/paper.pdf`，不重命名、不修改内容。
- FR-1.5 入库全过程异步执行，前端可查看进度与失败原因。

### FR-2 论文主表

- FR-2.1 建立论文表，字段至少包含：**论文名、作者（含单位）、期刊、刊发时间、哈希编码值**。
- FR-2.2 哈希作为唯一索引，用于加速查找与去重。
- FR-2.3 作者与单位为一对多关系（一个作者可挂多个单位，一个单位可有多个作者）。
- FR-2.4 支持按论文名、作者名、哈希、期刊、年份范围检索。
- FR-2.5 论文表与其它数据表之间通过哈希建立外键关联，删除论文时级联清理。

### FR-3 PDF 解析（视觉大模型直读）

- FR-3.1 解析方式为**把 PDF 直接发送给支持视觉/文档输入的大模型**，由模型返回结构化结果。
- FR-3.2 解析结果至少包含：标题、作者及单位、期刊/会议、刊发时间、摘要、关键词、语言、
  章节结构与正文、图表标题与说明。
- FR-3.3 模型返回必须是可校验的 JSON；校验失败时按既定策略重试（降低温度、追加纠错提示）。
- FR-3.4 超大 PDF 采用分批送模（按页区间切分）后合并策略，避免超出上下文与请求体积上限。
- FR-3.5 解析结果附带原始响应留存，便于追溯与重新解析。

### FR-4 图表裁剪与存储

- FR-4.1 图、表由 Python 库（PyMuPDF）在本地裁剪为图片。
- FR-4.2 命名规则：图按 `fig1`、`fig2`…，表按 `tab1`、`tab2`…，按论文内出现顺序编号。
- FR-4.3 图存放在 `papers/<hash>/fig/`，表存放在 `papers/<hash>/tab/`。
- FR-4.4 每张图/表记录：标签、页码、边界框、标题说明、文件相对路径。
- FR-4.5 裁剪失败或被模型判定为无图表的论文，允许 `fig/`、`tab/` 为空目录。

### FR-5 OKF 格式存储

- FR-5.1 每篇论文的解析结果以 OKF v0.2 格式完整落盘为一棵 Bundle 目录树。
- FR-5.2 Bundle 内包含：根 `index.md`、`log.md`、论文总览概念、章节概念、图表概念。
- FR-5.3 每个概念文档必须具备合法 YAML frontmatter，且含非空 `type` 字段。
- FR-5.4 概念之间使用 Markdown 链接建立关系，图表概念链接到实际图片文件。
- FR-5.5 提供 OKF 一致性校验（相当于规范 §11 的 conformance 检查）。
- FR-5.6 OKF Bundle 可在软件内浏览：目录树 + 文档渲染。

### FR-6 金字塔式 RAG 语义库

- FR-6.1 从原文精简，提取大意，写入 **RAG 库 A**。
- FR-6.2 将大意 A 再精简，写入 **RAG 库 B**。
- FR-6.3 将 abstract 部分写入 **RAG 库 C**。
- FR-6.4 A、B、C 构成金字塔型语义存储：C 在最上层（最凝练），B 居中，A 在最下层（最详细）。
- FR-6.5 相邻层之间建立联系：A↔B、B↔C 均为可双向追溯的关联。
- FR-6.6 C 层还要与其它论文的 C 层建立联系（跨论文关联）。
- FR-6.7 每个语义单元记录来源论文哈希、所属层、所属鱼骨维度、来源 OKF 概念、顺序号。

### FR-7 鱼骨式知识图谱

- FR-7.1 知识图谱以 **RAG 库 B** 为语料来源。
- FR-7.2 图谱骨架按论文行文顺序固定为七段：背景、数据、方法、实验、结论、讨论、不足与展望。
- FR-7.3 骨架之上挂载更详细的内容节点。
- FR-7.4 图表以**存储地址链接**的形式挂载到对应内容节点，不复制图片数据。
- FR-7.5 支持按论文查看单篇鱼骨图，也支持多篇论文的跨论文图谱视图。
- FR-7.6 支持图谱导出（JSON / GraphML）。

### FR-8 论文查看

- FR-8.1 软件内可查看原始 PDF（内嵌阅读器）。
- FR-8.2 软件内可查看 OKF 存储内容（目录树 + Markdown 渲染）。
- FR-8.3 软件内可查看图表列表与单张图表大图。

### FR-9 技能（Skill）装载

- FR-9.1 支持从本地目录或压缩包安装 Skill。
- FR-9.2 Skill 以 `SKILL.md`（YAML frontmatter + 正文指令）为清单文件。
- FR-9.3 Skill 可声明其提供的工具（声明式 HTTP/脚本工具）。
- FR-9.4 支持启用、禁用、卸载、查看 Skill 详情。
- FR-9.5 已启用 Skill 的指令注入智能体系统提示，其工具进入工具注册表。

### FR-10 多智能体隔离头脑风暴

- FR-10.1 支持针对单篇或多篇论文、或一个开放问题发起头脑风暴。
- FR-10.2 每个子智能体拥有**隔离**的：会话上下文、工作目录、工具白名单、可见论文范围。
- FR-10.3 支持由用户指定或系统推荐多个角色（persona），并可为不同角色指定不同模型。
- FR-10.4 第一轮为独立分析，子智能体之间互不可见，避免相互污染。
- FR-10.5 后续轮次通过共享黑板（由主持人汇总）交换观点，而非直接共享完整上下文。
- FR-10.6 由主持人智能体在末轮汇总为结构化结论。
- FR-10.7 全过程记录每个发言的归属智能体，可在前端回放。

### FR-11 基于 RAG 的问答

- FR-11.1 问答必须基于 RAG 库作答，不得凭空生成。
- FR-11.2 检索顺序为 **C、B、A**：先在 C 层定位最相关论文/主题，再下钻到 B 层看要点，
  必要时再下钻到 A 层看细节。
- FR-11.3 回答必须给出引用来源：论文哈希、论文名、所在层、所属章节或鱼骨维度。
- FR-11.4 若库中无相关内容，必须明确说明「库中无相关内容」，不得编造。
- FR-11.5 支持限定检索范围为勾选的若干篇论文。
- FR-11.6 支持流式输出。

### FR-12 前端交互

- FR-12.1 支持勾选单篇或多篇论文作为操作对象。
- FR-12.2 支持按哈希表、论文名、作者等条件查找论文。
- FR-12.3 界面风格为毛玻璃（glassmorphism）。
- FR-12.4 布局参考 DeepSeek 的侧栏 + 主区结构，但为**多页面**应用。
- FR-12.5 禁止使用 emoji 等各类小符号，只使用文字按钮。
- FR-12.6 前端功能必须与后端接口严格对齐，不出现调用不存在接口的情况。

### FR-13 多数据库之间的联系

- FR-13.1 关系库（论文表/作者/单位/资产/语义单元/图谱/会话）之间以外键与哈希互相约束。
- FR-13.2 向量库（ChromaDB 三个集合）与关系库通过语义单元 ID 一一对应。
- FR-13.3 图谱库与关系库通过节点键、论文哈希、资产 ID 对应。
- FR-13.4 OKF 文件树是「可读的真相来源」之一，关系库中记录每个概念的来源路径。
- FR-13.5 删除论文时，关系库级联、向量库按论文删除、图谱按论文删除、文件目录整体移除，
  四者保持一致。

### FR-14 设置与配置

- FR-14.1 支持配置多个大模型提供方（OpenAI 兼容协议），每个提供方含 Base URL、API Key、模型名。
- FR-14.2 支持分别指定：解析模型（需支持 PDF/视觉输入）、问答模型、嵌入模型。
- FR-14.3 API Key 仅保存在本地配置文件，不回传到前端明文展示（回显为掩码）。
- FR-14.4 支持配置数据目录、嵌入提供方（本地模型 / 远程接口 / 离线词法）。

## 4. 非功能需求

| 编号 | 需求 |
| --- | --- |
| NFR-1 | **跨操作系统**：Windows、macOS、Linux 均可运行，减少跨系统开发工作量 |
| NFR-2 | **跨端通信**：前后端通过 HTTP + SSE 通信，接口有明确契约与类型 |
| NFR-3 | **性能**：单篇论文入库（不含大模型耗时）应在秒级完成；检索在千级语义单元下响应 < 1s |
| NFR-4 | **健壮性**：大模型返回异常、网络中断、PDF 损坏均须记录并可重试，不得使服务崩溃 |
| NFR-5 | **可观测**：入库与智能体运行过程产生结构化日志，前端可看到分阶段进度 |
| NFR-6 | **可离线降级**：无网络时，本地嵌入模型或离线词法检索仍可工作；仅大模型调用不可用 |
| NFR-7 | **可测试**：核心逻辑（哈希、OKF 校验、金字塔构建、检索）具备单元测试 |
| NFR-8 | **数据安全**：删除论文为显式确认操作，且清理全部关联数据 |

## 5. 验收标准

1. 导入一篇真实论文 PDF，能产出：原 PDF、`fig/`、`tab/`、OKF Bundle、A/B/C 三层语义单元、
   七维鱼骨图谱，且论文表记录完整（论文名/作者含单位/期刊/刊发时间/哈希）。
2. 重复导入同一 PDF，被哈希去重拦截，不产生重复记录。
3. 在问答页提问，回答带引用，且引用可跳转到对应论文与层级。
4. 勾选两篇论文发起头脑风暴，可看到多个隔离智能体的独立发言与主持人汇总。
5. 装载一个 Skill 后，其指令与工具对智能体生效；禁用后失效。
6. 论文详情页可查看 PDF 原文、OKF 文档、图表；图谱页可见七维骨架。
7. 前端所有页面调用的接口均在后端存在，构建无报错。
